처음 방문한 분께

CodeReferee는 공개 GitHub 레포를 격리 환경에서 실행하고, 선택한 장애에 대한 응답과 복구를 관측합니다. 먼저 간단한 단일 HTTP 서비스로 체험해 보세요.

현장에서는 이 순서로 진행하세요

  1. 공개 GitHub 레포 URL을 입력합니다. 다른 브랜치에 코드가 있으면 브랜치도 입력합니다.
  2. 실험 종류에서 빠른 검사를 선택합니다. 제출한 서비스에 Container Kill을 적용해 복구를 관측합니다.
  3. 배포 프로필은 우선 비워둡니다. 지원되는 실행 환경과 레포 설정을 자동 탐색합니다.
  4. 결과 메일을 받으려면 본인 이메일을 입력합니다. 발송은 운영 메일 설정과 정상 완료 여부에 따릅니다.
  5. 접수 후 작업 ID와 결과 주소를 보관합니다. 요청은 현재 한 건씩 처리돼 대기할 수 있습니다.

설정 없이 먼저 시도하기 좋은 레포

레포 루트에 실행 대상이 하나 있고, 지원하는 빌드/실행 방식이 있으며, 테스트용 환경에서 시작할 수 있는 HTTP 앱입니다. 단순한 FastAPI·Flask·Node·Spring Boot 앱이나 단일 HTTP 포트를 노출하는 Dockerfile이 대표적입니다.

설정이 복잡하면 부스에서 받아 가세요

여러 서비스·외부 인증·별도 비밀값이 필요한 프로젝트는 환경 확인에 시간이 걸릴 수 있습니다. 양식과 가이드를 받아 설정을 준비한 뒤 다시 요청할 수 있습니다.

검사는 수 분 이상 걸릴 수 있고, 대기와 자동 수정으로 더 길어질 수 있습니다. 기본 응답 검사와 서비스 전체 업무의 정확성 검사는 범위가 다릅니다.

설정 없이 가능한 범위

레포 구성자동 탐색 조건
Pythonapp.py / main.py / app/main.py의 FastAPI, 루트 Flask 앱 등 지원 패턴
Node / Vitepackage.json의 실행 스크립트 또는 지원되는 Vite 정적 빌드
Spring Boot지원 Maven/Gradle 구성과 실행 아티팩트를 찾을 수 있는 구조
Dockerfile루트 Dockerfile에 하나의 TCP 포트가 명확하고 검사·실행 조건이 충족되는 구성
Compose빌드할 HTTP 앱이 정확히 하나이며 지원 DB/Redis 등과 함께 있는 제한된 구성

의존성 설치·빌드·발견 가능한 테스트·기동·HTTP 응답을 확인합니다. 테스트 실행 여부는 실제 결과에서 확인해야 합니다. Chaos는 선택한 실험에 따라 수행합니다.

다음 경우에는 설정을 준비하세요

  1. 실행할 서비스가 여러 개이거나 하위 디렉토리 선택이 필요할 때
  2. 포트가 없거나 여러 개여서 HTTP 대상이 불명확할 때
  3. 실행 환경변수·DB·Redis·명시적 검사 명령이 필요할 때
  4. 여러 레포를 함께 띄우거나 서비스 간 연결을 정의해야 할 때
  5. 업무 API의 요청 순서·기대 응답 또는 화면 동작을 검증할 때

지원되는 로컬 DB 설정은 자동 탐색할 수 있습니다. 사설 레포, 미지원 스택·의존성, 외부 서비스 자격증명, 무거운 빌드 등은 추가 설정이나 지원 범위 확인이 필요합니다. 모든 레포의 실행 성공을 보장하지 않습니다.

양식 선택과 반영 방법

내 상황받을 양식
자동 실행되며 복제본/자원만 조정01-auto-override.yaml
단일 서비스의 실행 설정 지정02-single-service.yaml
한 레포의 여러 앱 서비스03-multi-service.yaml
여러 레포의 서비스 그룹04-multi-repository.yaml
업무 요청/화면 검사 추가05-business-browser-fragment.yaml
  1. 양식 주석을 읽고 실제 경로·Dockerfile·포트·환경변수로 수정합니다.
  2. UTF-8 validation.yaml로 저장하고 요청 화면의 검증 설정 YAML에 첨부합니다(64KiB 이하).
  3. 업로드는 레포 설정 파일보다 우선하며 임시 clone에만 적용합니다. GitHub 커밋 없이 검사와 재검증에 유지됩니다.
  4. 레포 URL·브랜치·선택 SHA를 입력합니다. SQL 등 참조 파일은 해당 커밋에 있어야 합니다.
  5. 배포 프로필은 비웁니다. 레포의 .codereferee/validation.yaml에 저장·push하는 방식도 선택할 수 있습니다.

단일 서비스 예시

version: 1
service:
  buildContext: .
  dockerfile: Dockerfile
  port: 8000
  healthPath: /
  env:
    APP_ENV: demo

Dockerfile 경로는 해당 레포 루트 기준입니다. buildContext는 Docker가 읽을 빌드 디렉토리입니다. 환경변수 이름은 앱이 실제로 읽는 이름과 같아야 합니다. 운영 비밀번호 대신 재현용 값을 사용하고, 관리형 의존성의 비밀번호는 Sandbox 템플릿을 사용합니다.

여러 서비스와 레포 연결

version 2는 한 레포 안의 여러 서비스를 선언합니다. version 3는 repositories에 추가 소스를 선언하고 각 서비스의 repository로 소유 레포를 연결합니다. main은 제출한 레포를 뜻합니다.

필드정할 내용
buildContext / dockerfile / port각 서비스의 빌드 위치·이미지 정의·접속 포트
env / dependsOn서비스 연결 정보와 다른 앱 서비스의 준비 순서
entryService검증 HTTP 요청이 들어갈 서비스
targetService선택한 앱 장애를 주입할 서비스
probePath / probeSpec진입 서비스에서 호출할 업무 경로와 기대 응답
repositories추가 공개 GitHub URL, 브랜치와 선택적 고정 SHA

주소는 Sandbox가 채웁니다

API_URL: '{{service.api.url}}'
REDIS_HOST: '{{dependency.redis.host}}'
REDIS_PORT: '{{dependency.redis.port}}'
DB_PASSWORD: '{{dependency.database.password}}'

템플릿으로 주소를 넣어도 앱의 프록시나 클라이언트 코드는 그 변수를 사용하도록 구현돼 있어야 합니다. gateway로 보낸 업무 요청이 api와 DB/Redis를 실제로 통과하는 경로를 선택하세요.

업무·화면 검증 확장

probeSpec은 생성 요청 → 응답 ID 추출 → 조회와 JSON 필드 확인 등을 지원합니다. browserProbe는 진입 서비스의 화면에서 이동·입력·클릭·텍스트 확인 등을 수행합니다. 05번 파일은 version 2/3 설정에 합치는 선택 조각입니다.

하나의 요청은 지정한 앱 대상에 장애를 적용합니다. 서비스 전체 자동 순회는 후속 범위입니다. DB/Redis 장애는 선언한 의존성을 대상으로 별도 실행됩니다.

지원 제한과 결과 읽기

항목현재 지원
앱 서비스 그룹2~5개. 단일 서비스는 version 1 사용
추가 레포1~4개. 제출 레포를 포함하면 최대 5개
관리형 의존성최대 8개. Redis / PostgreSQL / MySQL
서비스 복제본서비스당 1~4개
업무 probesetup/steps 각각 최대 8개 요청
배포 격리요청별 namespace. 현재 단일 Sandbox에서 순차 처리

Kafka 등 다른 종류를 dependencies.type으로 선언하면 설정 오류로 거절됩니다. 앱을 선언 서비스로 구성하는 별도 방식까지 자동 지원한다는 뜻은 아닙니다. 의존성 장애 업무 probe는 현재 Redis 1개와 DB 1개까지 지정할 수 있습니다.

결과가 이렇게 나오면

  1. PASSED: 이번에 실행한 검사와 판정 기준을 통과했습니다.
  2. FAILED: 원본의 관측된 복원력이 판정 기준을 충족하지 못했습니다. 수정본 통과 기록과 검증된 패치가 함께 있을 수 있습니다.
  3. ERROR: 실행 환경·시간 예산·설정 등으로 판정할 근거를 확보하지 못했습니다. 상세 단계와 로그를 확인하세요.
  4. 설정 제한 초과: 서비스 수·추가 레포 수·의존성 종류와 실제 파일 경로를 확인하세요. 현재 화면의 일반 문구만으로 원인을 다 알기 어려워 상세 보고서도 확인해야 합니다.

복구 시간 0초는 HTTP 표본에서 중단을 포착하지 않았다는 의미입니다. 전체 업무의 무중단 보장을 뜻하지 않습니다. 재검증 통과 시에도 원본 판정은 유지되고 patch_verified와 회차 기록에 수정 결과가 남습니다.

검증 요청은 하나씩 처리됩니다. 이메일 수신을 선택한 경우 작업 ID와 결과 주소도 함께 보관하세요. 전시 부스에서 해석이 어려운 결과는 운영자에게 문의해 주세요.

양식 다운로드와 복사

전체 파일은 01~04 중 하나를 선택하세요. 05는 기존 version 2/3 파일에 합치는 선택 조각입니다. validation.yaml로 저장해 요청 화면에 업로드하면 GitHub에 커밋할 필요가 없습니다. 반복 사용하려면 레포의 .codereferee/validation.yaml에 저장하는 방식도 선택할 수 있습니다.

01-auto-override.yaml이 양식 받기
# 자동 탐색으로 이미 실행되는 단일 서비스의 복제본/자원만 바꿀 때 사용합니다.
# 이 양식은 실행 명령이나 포트를 새로 지정하지 않습니다.
# 사용: 요청 화면에 업로드하거나 레포의 .codereferee/validation.yaml에 저장
version: 1
service:
  replicas: 2
  resources:
    cpu: 1000m
    memory: 512Mi
02-single-service.yaml이 양식 받기
# 단일 HTTP 서비스. Dockerfile/포트/환경변수는 내 프로젝트에 맞게 수정합니다.
# Dockerfile 경로는 레포 루트 기준입니다. 해당 파일이 실제로 존재해야 합니다.
# 사용: 요청 화면에 업로드하거나 레포의 .codereferee/validation.yaml에 저장

03-multi-service.yaml이 양식 받기
# 한 레포의 gateway/ 와 api/ 를 각각 배포하는 예시입니다.
# 두 디렉토리와 Dockerfile을 실제 경로로 바꾸세요.
# API_URL/REDIS_HOST/REDIS_PORT는 앱이 실제로 읽는 환경변수 이름으로 바꾸세요.
# gateway 앱이 API_URL을 사용해 /api/ 요청을 api로 전달하도록 구현돼 있어야 합니다.
version: 2
services:
  gateway:
    buildContext: gateway
    dockerfile: gateway/Dockerfile
    port: 8080
    healthPath: /health
    dependsOn: [api]
    env:
      API_URL: '{{service.api.url}}'
  api:
    buildContext: api
    dockerfile: api/Dockerfile
    port: 8000
    healthPath: /health
    env:
      REDIS_HOST: '{{dependency.redis.host}}'
      REDIS_PORT: '{{dependency.redis.port}}'
dependencies:
  redis:
    type: redis
    probePath: /api/items/1
entryService: gateway
targetService: api
# 이 경로는 gateway에서 접근 가능하고, 실제 Redis 업무를 수행해야 합니다.
probePath: /api/items/1
# Redis가 필요 없는 앱이면 dependencies와 관련 env를 함께 제거하세요.
04-multi-repository.yaml이 양식 받기
# 제출한 레포(main)는 gateway를, 추가 레포(backend)는 api를 제공합니다.
# URL은 자리표시자입니다. 공개 HTTPS GitHub 레포 주소로 반드시 바꾸세요.
version: 3
repositories:
  backend:
    url: https://github.com/your-team/your-api.git
    branch: main
    # 재현할 버전을 고정하려면 실제 40자리 소문자 SHA를 추가하세요.
    # commitSha: 실제_40자리_SHA
services:
  gateway:
    repository: main
    buildContext: gateway
    dockerfile: gateway/Dockerfile
    port: 8080
    healthPath: /health
    dependsOn: [api]
    env:
      API_URL: '{{service.api.url}}'
  api:
    repository: backend
    buildContext: .
    dockerfile: Dockerfile
    port: 8000
    healthPath: /health
entryService: gateway
targetService: api
# gateway가 실제로 제공하는 업무 경로로 수정하세요.
probePath: /api/items/1
05-business-browser-fragment.yaml이 양식 받기
# 독립 실행용 파일이 아닙니다. version 2 또는 3 설정의 최상위에 합치세요.
# API 경로/요청 본문/응답 필드/화면 선택자를 실제 앱에 맞게 바꿉니다.
probePath: /api/items
probeSpec:
  setup:
    - path: /api/items
      method: POST
      body: {label: 'demo-${runId}'}
      extract: {itemId: id}
  steps:
    - path: '/api/items/${itemId}'
      expect: {saved: true, label: 'demo-${runId}'}
