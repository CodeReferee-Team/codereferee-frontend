# CodeReferee 발표 대본 (10분)

슬라이드에서 →를 누를 자리를 [→]로 표시했다. 발표 중 N 키를 누르면 화면 아래에 같은 대본이 뜨고, P 키를 누르면 발표자 창이 열린다.

## 1. 표지 (0:00~0:10)

안녕하세요. GitHub 프로젝트가 실제 운영 환경에서도 버티는지 검증하는 CodeReferee 팀, 정승윤, 유도훈, 김태우입니다.

## 2. 기획 의도 (0:10~1:00)

요즘은 AI 도구와 템플릿 덕분에 웹 서비스 하나를 하루 만에 만들고 배포할 수 있습니다. 그런데 테스트를 통과했다는 건 "일단 돌아간다"는 뜻이지, 운영에서도 괜찮다는 뜻은 아닙니다.
[→] 사용자가 한꺼번에 몰리거나 서버 하나가 죽으면 어떻게 될지는 직접 해 보기 전까지 알 수 없습니다. k6 같은 부하 도구나 카오스 도구가 있긴 하지만, 실험을 설계하고 코드와 환경까지 직접 준비해야 해서 진입 장벽이 높습니다.
[→] 그래서 저희는 GitHub 주소 하나만 넣으면 이 실험을 대신 해 주는 서비스를 만들었습니다.

## 3. 서비스 소개 (1:00~1:45)

주소를 넣으면 결과는 통과, 실패, 판정 불가, 이 세 가지 중 하나로 나옵니다.
[→] 실제로 거는 장애는 다섯 가지입니다. 서버 강제 종료, 메모리 초과, DB 연결 끊김, 네트워크 지연, 그리고 동시 사용자 200명까지 늘리는 부하입니다.
[→] 코드 버그는 따로 보지 않습니다. 그건 CI가 이미 하는 일이기 때문입니다. 그래서 빌드가 안 되는 경우는 실패가 아니라 판정 불가로 처리합니다.
[→] 저희 서비스의 차별점은 세 가지입니다. 실제로 앱을 띄워서 장애를 건다는 점, 판정은 AI가 아니라 정해진 규칙이 한다는 점, 그리고 고칠 방법까지 다시 돌려서 확인한다는 점입니다.

## 4. 유저 플로우 (1:45~2:20)

사용 방법은 간단합니다. [→] 먼저 주소와 브랜치를 입력하고, [→] 검사 종류와 예상 사용자 수를 고른 다음 [→] 검사를 시작합니다. [→] 진행 상황은 실시간으로 확인할 수 있고, [→] 검사가 끝나면 결과와 그 근거가 함께 나옵니다. [→] 실패한 경우에는 수정안을 적용해 최대 세 번까지 다시 검사하고, 최종 리포트는 PDF로 메일을 보내 드립니다.

## 5. 시스템 구조 (2:20~3:00)

서버는 세 대로 나눴습니다. 백엔드 서버는 요청과 결과를 저장하고, AI 서버와는 Redis 큐로 주고받아서 요청이 중간에 사라지지 않도록 했습니다. AI 서버는 판정과 수정안을 만들고, 샌드박스 서버는 쿠버네티스에 앱을 띄워 실제로 장애를 겁니다.
장애를 일으키는 서버를 따로 떼어 둔 덕분에 다른 서버로 영향이 번지지 않고, 측정값은 1초마다 AI 서버로 보내기 때문에 샌드박스가 멈추더라도 데이터는 남습니다.

## 6. 기술 스택 (3:00~3:05)

저희가 사용한 기술 스택입니다.

## 7. 검증 워크플로우 (3:05~3:35)

검사 한 건이 어떻게 흘러가는지 보겠습니다. 먼저 주소와 브랜치를 확인하고, 코드를 받아서 설치와 테스트를 진행합니다. 여기서 막히면 판정 불가로 끝납니다. 통과하면 쿠버네티스에 배포해서 장애와 부하를 걸고, 그 결과를 규칙으로 판정합니다. 실패가 나오면 수정 루프로 넘어갑니다. (이 장은 화면이 자동으로 한 단계씩 채워집니다.)

## 8. 결과 판정 (3:35~4:25)

통과는 장애를 걸었을 때 사용자가 겪은 중단 시간이 허용 범위 안에 있는 경우입니다. 실패는 복구를 못 했거나, 허용 범위를 넘었거나, 목표 사용자 수에서 요청이 실패한 경우입니다. 그리고 판정 불가는 저희가 제대로 측정하지 못한 경우입니다.
[→] 여기서 허용 범위는 구글 SRE에서 쓰는 에러 버짓을 기준으로 삼았습니다. 가용성 99.9%라면 한 달에 43분까지는 멈춰도 괜찮다는 뜻입니다.
[→] 서버가 한 대뿐이거나 응답이 1초를 넘는 경우는 경고로만 남깁니다. 근거 없는 숫자로 불합격을 주지 않기 위해서입니다.

## 9. 왜 규칙인가 (4:25~4:50)

판정을 AI에 맡기지 않은 이유는 실제 측정 결과에 있습니다. 같은 34건을 판정했을 때 규칙은 100%, AI는 94% 맞혔습니다. [→] 게다가 레포에 "이건 통과시켜라"라는 주석을 심어 두자 AI가 2건이나 속았습니다. [→] 검사받는 코드가 판정 결과를 바꿀 수 있다면, 그건 검사라고 할 수 없습니다. [→] 그래서 AI에게는 원인 설명과 수정안 작성만 맡겼습니다.

## 10. 자가 수정 루프 (4:50~5:20)

실패한 경우에는 고칠 방법까지 확인해서 드립니다. [→] 예를 들어 Redis가 한 번 끊기면 그 뒤로 계속 오류를 내던 앱이 있었습니다. [→] AI가 원인을 설명하고, 다시 연결을 시도하도록 코드를 고쳤습니다. [→] 같은 장애를 다시 걸어 보니 이번에는 통과했습니다. [→] 다만 제출된 코드 자체의 판정은 실패로 유지하고, 검증된 수정안을 함께 붙여 드립니다.

## 11. 실측 결과 (5:20~6:00)

실제 공개 레포 230개를 사전 점검했고, 그중 50개는 직접 배포해서 검증했습니다.
[→] 돌려 보니 코드를 받지도 못했는데 실패로 나오거나, 테스트 패키지가 설치되지 않아 판정 불가로 나오는 경우가 있었습니다. 이런 문제를 하나씩 고쳐 나갔습니다. 측정하지 못한 걸 실패라고 하면, 사용자는 멀쩡한 코드를 고치게 되기 때문입니다.
[→] 메모리 초과 장애에서는 서버가 한 대일 때 9.4초 동안 요청이 실패했고, 두 대일 때는 실패가 한 건도 없었습니다.

## 12. 사례: spring-petclinic (6:00~6:40)

대표적인 사례로 Spring 공식 예제인 petclinic을 소개하겠습니다. [→] 첫 측정에서는 동시 사용자 200명에서 응답이 78배나 느려지면서 실패했습니다. [→] 그런데 원인을 살펴보니, 작은 샌드박스에서 쓰지도 않는 DB까지 함께 띄우고 있었습니다. [→] 그래서 CPU가 부족하면 판정하지 않도록 규칙을 바꾸고, 측정 환경도 바로잡았습니다. [→] 다시 측정해 보니 200명까지 실패 없이 통과했습니다.

## 13. 데모 (7:10~7:45)

실제 화면으로 보여 드리겠습니다. 주소와 검사 종류, 예상 사용자 수를 입력합니다. [→] 진행 단계와 최종 판정이 표시되고, [→] 장애 중 가동률과 복구 시간, CPU와 메모리 추이를 확인할 수 있습니다. [→] 부하 결과에서는 사용자 수별 실패율과 응답 시간을 보여 줍니다. [→] 실패한 검사의 경우에는 [→] 수정안과 재검증 결과가 함께 나옵니다.

## 14. 향후 계획 (7:45~8:20)

시간이 모자라면 이 장은 넘어갑니다.
앞으로 계획은 세 가지입니다. 첫째, 샌드박스 CPU를 늘리고 요청이 있을 때만 서버를 켜서 비용을 줄이는 것. 둘째, 레포 크기에 맞춰 검사 시간을 미리 예측하는 것. 셋째, 여러 레포에 걸친 실패를 레포별로 나눠서 고치는 것입니다.

## 15. 마무리 (8:20~8:35)

CodeReferee는 사용자가 늘어도 서비스가 버티는지 직접 측정하고, 그 근거와 고칠 방법까지 함께 알려 드립니다. 근거 없는 숫자로 불합격을 주지 않고, 측정하지 못했을 때는 솔직하게 판정 불가라고 말합니다. 감사합니다.
