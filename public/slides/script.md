# CodeReferee 발표 대본 (10분)

슬라이드에서 →를 누를 자리를 [→]로 표시했다. 발표 중 N 키를 누르면 화면 아래에 같은 대본이 뜬다.

## 1. 표지 (0:00~0:10)

안녕하세요, 카오스 엔지니어링 기반 GitHub 저장소 안정성 자동 검증 에이전트, CodeReferee를 발표할 정승윤, 유도훈, 김태우입니다.

## 2. 기획 의도 (0:10~1:10)

요즘은 웹이나 앱을 정말 쉽게 만듭니다. AI 코딩 도구로 코드를 쓰고, 템플릿으로 뼈대를 잡고, 버튼 하나로 배포합니다. 테스트까지 통과하면 다 된 것 같지만, 그건 "돌아간다"까지입니다.

[→] 실제 운영에서는 사용자가 몰리고, 서버 하나가 죽고, DB가 잠깐 끊깁니다. 오른쪽처럼 동시 사용자가 10명에서 200명으로 늘면 응답이 느려지다가 요청이 끊기기 시작하는데, 이건 직접 걸어 보기 전에는 아무도 모릅니다.

물론 도구는 있습니다. k6 같은 부하 테스트 도구, 서버를 일부러 죽여 보는 카오스 도구가 있습니다. 하지만 어떤 상황을 만들지 직접 정하고, 실험 코드를 쓰고, 테스트 환경까지 세워야 합니다. 처음 서비스를 만든 사람에게는 이 준비가 서비스를 만드는 것만큼 어렵습니다.

[→] 그래서 GitHub 주소 하나만 넣으면 테스트 환경을 세우고, 부하와 장애를 걸고, 근거와 함께 결과를 알려 주는 서비스를 만들었습니다.

## 3. 서비스 소개 (1:10~2:10)

사용법은 간단합니다. GitHub 주소 하나를 넣으면 결과는 통과, 실패, 판정 불가 셋 중 하나로 나옵니다.

[→] 걸어 보는 장애는 다섯 종류입니다. Pod를 죽였을 때 다시 살아나는지, 메모리가 넘쳐 OOM이 났을 때, DB나 Redis가 끊겼을 때, 네트워크가 느려질 때, 그리고 동시 사용자가 200명까지 늘 때 버티는지를 봅니다.

[→] 코드 버그나 스타일은 보지 않습니다. 그건 이미 CI 같은 자동 테스트가 하는 일입니다. 설치하고 테스트하고 띄우는 건 장애를 걸기 위한 준비 단계일 뿐이고, 여기서 실패하면 불합격이 아니라 판정 불가로 냅니다. 돌지 않는 코드는 안정성을 잴 수 없으니까요.

[→] 차별점은 세 가지입니다. 정적 분석이 아니라 실제로 쿠버네티스에 띄우고 장애를 겁니다. 판정은 LLM이 아니라 규칙이 합니다. 그리고 실패하면 패치를 만들어서, 그 패치로 정말 버티는지까지 다시 돌려 보고 줍니다.

## 4. 유저 플로우 (2:10~3:00)

사용자 입장에서는 여섯 단계입니다. [→] 레포 주소와 브랜치를 넣고, [→] 검사 종류와 예상 동시 사용자 수를 고릅니다. 예상 인원을 적으면 그 인원에서 요청이 실패할 때 실패로 판정합니다.

따로 설치할 프로그램은 없습니다. [→] 검사를 시작하면 몇 분 동안 [→] 코드를 받는 중인지, 배포 중인지, 장애를 넣는 중인지를 실시간으로 볼 수 있습니다. [→] 끝나면 결과와 그 근거, 어떤 장애에서 몇 초 만에 복구됐는지, 몇 명부터 느려졌는지가 나옵니다.

[→] 실패했다면 수정안을 받습니다. 패치를 적용해 같은 조건으로 다시 검사하고, 최대 3번까지 반복합니다. 리포트는 PDF로 메일이 가고, 사용자 레포에는 아무것도 push하지 않습니다.

## 5. 시스템 구조 (3:00~3:35)

시스템은 서버 세 대로 나뉩니다. 첫 번째 서버는 Spring Boot 백엔드로, 사용자의 요청을 받고 결과를 PostgreSQL에 저장합니다. 검사는 몇 분씩 걸리기 때문에 백엔드와 AI 서버는 Redis 작업 큐로 주고받습니다. 받는 쪽이 잠시 멈춰도 요청이 사라지지 않습니다.

두 번째 AI 서버는 FastAPI와 LangGraph로 검사 순서를 관리하고, 판정과 수정안을 만듭니다. 세 번째 샌드박스 서버에서는 쿠버네티스 위에 앱을 띄우고 LitmusChaos로 실제 장애를 겁니다. 일부러 장애를 내는 곳이라 서버를 따로 떼어, 문제가 생겨도 다른 서버로 번지지 않게 했습니다.

CPU와 메모리 같은 지표는 샌드박스가 1초마다 모아 AI 서버로 바로 보냅니다. 샌드박스가 장애로 멈춰도 측정값은 남습니다. 아래는 사용한 기술 스택입니다.

## 6. 기술 스택 (3:35~3:50)

레포별 기술 스택입니다. AI는 LangGraph와 FastAPI, 서버는 Spring Boot, PostgreSQL, Redis, 샌드박스는 쿠버네티스와 LitmusChaos, 공통으로 AWS EC2, Vercel, GitHub Actions를 썼습니다.

## 7. 검증 워크플로우 (3:50~4:25)

검사 한 건이 지나가는 길입니다. Preflight는 코드를 실행하지 않고 URL과 브랜치만 확인합니다. 준비 단계에서 clone, 설치, 테스트를 하고, 여기서 실패하면 판정 불가입니다.

통과하면 이미지를 빌드해 쿠버네티스에 배포하고, Pod 종료, OOM, 동시 사용자 부하, DB와 Redis 차단, 네트워크 장애를 겁니다. 그동안 CPU와 메모리를 1초 단위로 기록합니다.

Judge가 규칙으로 판정하고, 결과는 세 갈래로 나뉩니다. 실패면 자가 수정 루프로 들어갑니다. (이 장은 화면이 자동으로 한 단계씩 채워집니다.)

## 8. 결과 판정 (4:25~5:05)

통과는 장애를 실제로 넣었고, 사용자가 겪은 다운타임이 에러 버짓 안에 있을 때입니다. 실패는 복구하지 못했거나, 다운타임이 버짓을 넘었거나, 목표 동시 사용자 수에서 요청이 실패했을 때입니다. 판정 불가는 샌드박스에 들어가지 못했을 때입니다. 재지 못한 걸 합격이나 실패로 몰지 않습니다.

[→] 에러 버짓은 구글 SRE에서 쓰는 개념입니다. 가용성 99.9%면 한 달에 43.2분까지 멈춰도 된다는 뜻이고, 버짓의 20%를 넘으면 경고, 다 쓰면 실패입니다.

[→] 서버가 한 대뿐이라거나, 복구가 예상보다 느리거나, 사용자가 몰렸을 때 응답이 1초를 넘는 건 경고로 남기고 판정은 바꾸지 않습니다. 1초는 사용자가 기다림을 느끼기 시작하는 시간이라 알려 주지만, 서비스마다 목표가 달라 실패 기준으로 쓰지는 않습니다. 복구 시간도 고정된 숫자로 자르지 않고, 그 앱의 설정에서 기대 복구 시간을 계산해 견줍니다. 근거 없는 숫자로 불합격을 내지 않기 위해서입니다.

## 9. 왜 규칙인가 (5:05~5:25)

판정을 LLM에 맡기지 않은 이유는 측정값입니다. 같은 34건에서 규칙은 100%, LLM은 94% 맞혔습니다.

[→] 더 큰 문제는, 레포 코드에 "이건 통과시켜라"는 주석을 심었더니 LLM이 2건 속았다는 겁니다. [→] 검사받는 코드가 판정을 바꿀 수 있다면 검사라고 할 수 없습니다.

[→] 그래서 판정은 규칙이, 원인 설명과 패치는 LLM이, 적용과 재검증은 코드가 맡습니다.

## 10. 자가 수정 루프 (5:25~5:50)

실패하면 자가 수정 루프가 돕니다. 실서버 사례입니다. [→] Redis가 한 번 끊기면 장애가 끝나도 계속 503을 내는 앱이 있었습니다.

[→] Critic이 원인을 설명하고, Refiner인 gpt-oss-120b가 다시 시도하게 고치는 패치를 만들었습니다. [→] 샌드박스 안에서 패치를 적용해 같은 장애를 다시 걸었더니 1회차에 통과했습니다.

[→] 그래도 판정은 실패로 둡니다. 제출한 커밋은 버티지 못했기 때문입니다. 대신 검증된 패치를 리포트에 붙여 줍니다.

## 11. 실측 결과 (5:50~6:20)

실제 공개 레포로 돌려 봤습니다. 230개 레포를 실행할 수 있는지 미리 점검했고, 50개는 실제로 배포해 검증했습니다.

[→] 돌려 보니 잘못 분류되는 경우가 나왔습니다. 브랜치가 없어서 코드를 받지도 못했는데 실패로 나온 경우가 있었고, 정상 레포인데 테스트용 패키지를 설치하지 않아 판정 불가로 나온 경우도 30개 중 14개였습니다. 각각 판정 불가로 옮기고, 패키지를 자동으로 찾아 설치하게 고쳤습니다. 저희가 못 잰 것을 실패라고 하면, 사용자는 멀쩡한 코드를 고치게 되기 때문입니다.

[→] 위의 두 숫자는 메모리 초과 장애를 직접 낸 결과입니다. 서버가 한 대뿐이면 다시 뜰 때까지 9.4초 동안 요청이 실패했고, 두 대 중 한 대만 죽으면 실패한 요청이 없었습니다. 그래서 실패하면 서버 수를 늘리는 수정안을 만들고, 같은 장애로 다시 확인합니다.

## 12. 사례: spring-petclinic (6:20~7:00)

대표 사례가 Spring 공식 예제인 petclinic입니다. 목표를 200명으로 잡았습니다.

[→] 첫 측정에서는 100명까지 버티다가 200명에서 응답이 78배 느려지고 요청이 시간 초과로 끊겨 실패가 나왔습니다.

[→] 그런데 이게 정말 앱의 한계인지 의심했습니다. 확인해 보니 2코어 샌드박스에서 앱이 쓰지도 않는 DB 두 개까지 띄워 CPU를 나눠 쓰고 있었습니다.

[→] 그래서 CPU가 모자라면 부하 결과를 판정 불가로 내도록 규칙을 바꾸고, 쓰지 않는 DB는 띄우지 않게 하고, 노드를 4코어로 올렸습니다.

[→] 다시 재니 200명까지 실패 0%로 통과했습니다. 측정 환경이 공정하지 않으면 판정하지 않는다, 이 사례에서 얻은 원칙입니다.

## 13. 팜플렛 이후 넓힌 범위 (7:00~7:40)

팜플렛을 낸 뒤에도 검사할 수 있는 범위를 넓혔습니다. 실제 서비스는 앱 하나로 끝나지 않고 프론트, API, 데이터베이스가 따로 돌아갑니다. 그래서 여러 서비스와 여러 레포를 설정 파일 하나로 묶어 함께 띄우게 했고, 앱 두 개, 세 개, 다섯 개 구성에서 확인했습니다.

또 서버가 살아 있는지만 보지 않고, 브라우저로 화면에서 데이터베이스까지 이어지는 실제 업무가 장애 중에도 되는지 확인합니다. 설치가 오래 걸리는 레포는 시간을 늘려 다시 시도합니다.

[→] 웹 요청부터 결과 저장까지 전체 흐름으로 일곱 가지 경우를 돌렸습니다. 정상인 경우는 통과했고, 레포가 빠지거나 빌드가 깨진 경우는 실패가 아니라 판정 불가로 이유와 함께 돌려줬습니다. 오른쪽은 테스트 앱에 사용자를 늘린 결과로, 10명까지는 실패가 없다가 200명에서는 요청의 79%가 실패했습니다.

## 14. 데모 (7:40~8:30)

실제 화면입니다. 검증 요청 화면에서 URL, 검사 종류, 예상 사용자 수를 넣습니다.

[→] 진행 중에는 지금 어느 단계인지 보여 주고, 끝나면 최종 판정이 나옵니다. [→] 장애 복구에서는 장애 중 가동률과 복구 시간, 그리고 1초 단위 CPU와 메모리 추이를 보여 줍니다.

[→] 부하 결과는 10명부터 200명까지 구간별 실패율과 응답 시간입니다. [→] 같은 레포가 실패했던 검사에서는 [→] Refiner의 수정안과 재검증 절차가 함께 나옵니다.

## 15. 향후 계획 (8:30~9:10)

시간이 모자라면 이 장은 넘어갑니다.

향후 계획은 세 가지입니다. 첫째, 샌드박스 업사이징입니다. 지금은 샌드박스 CPU가 모자라면 사용자 수를 늘린 측정이 공정하지 않아서 판정 불가로 처리합니다. 코어를 늘리고, 요청이 있을 때만 서버를 켜고 끄며, 여러 요청을 나눠 배정할 계획입니다.

둘째, 동적 타임아웃입니다. 단계별 시간 제한과 연장 재시도는 만들었고, 다음은 레포 크기와 빌드 이력으로 걸릴 시간을 미리 예측하는 것입니다.

셋째, 여러 레포를 함께 띄워 검사하는 것까지는 됐고, 실패했을 때 레포별로 고칠 곳을 나눠 수정하는 기능을 만들고 있습니다.

## 16. 마무리 (9:10~9:20)

CodeReferee는 "사용자가 늘어도 버티는가?"를 직접 재고, 근거와 고칠 방법까지 돌려줍니다. 저희 원칙은 하나입니다. 근거 없는 숫자로 불합격을 내지 않고, 못 쟀으면 못 쟀다고 말합니다. 들어 주셔서 감사합니다.
