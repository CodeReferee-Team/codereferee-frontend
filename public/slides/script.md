슬라이드에서 →를 누를 자리를 [→]로 표시했다. 발표 중 N 키를 누르면 화면 아래에 같은 대본이 뜨고, P 키를 누르면 발표자 창이 열린다.

## 1. 표지 (0:00~0:10)

## 2. 기획 의도 (0:10~1:00)

요즘은 AI 도구와 템플릿 덕분에 웹 서비스를 하루 만에 만들고 배포합니다. 하지만 테스트 통과는 "돌아간다"까지입니다.
[→] 사용자가 몰리거나 서버 하나가 죽으면 어떻게 될지는 직접 걸어 보기 전에는 모릅니다. k6 같은 부하 도구나 카오스 도구가 있지만, 실험을 설계하고 코드와 환경을 직접 준비해야 합니다.
[→] 그래서 GitHub 주소 하나로 이 실험을 대신해 주는 서비스를 만들었습니다.

## 3. 서비스 소개 (1:00~1:45)

주소를 넣으면 결과는 통과, 실패, 판정 불가 중 하나로 나옵니다.
[→] 서버 강제 종료, 메모리 초과, DB 끊김, 네트워크 지연, 그리고 동시 사용자 200명까지의 부하, 다섯 가지를 실제로 겁니다.
[→] 코드 버그는 보지 않습니다. 그건 CI가 하는 일이고, 빌드가 안 되면 실패가 아니라 판정 불가입니다.
[→] 차별점은 실제로 띄워 장애를 건다는 것, 판정은 AI가 아니라 규칙이 한다는 것, 그리고 고칠 방법까지 다시 돌려 확인한다는 것입니다.

## 4. 유저 플로우 (1:45~2:20)

사용 방법입니다. [→] 주소와 브랜치를 넣고, [→] 검사 종류와 예상 사용자 수를 고른 뒤 [→] 시작합니다. [→] 진행 단계는 실시간으로 보이고, [→] 끝나면 결과와 근거가 나옵니다. [→] 실패하면 수정안을 적용해 최대 세 번 다시 검사하고, 리포트는 PDF로 메일이 갑니다.

## 5. 시스템 구조 (2:20~3:00)

서버는 세 대입니다. 백엔드는 요청과 결과를 저장하고, AI 서버와는 Redis 큐로 주고받아 요청이 사라지지 않게 했습니다. AI 서버는 판정과 수정안을 만들고, 샌드박스 서버는 쿠버네티스에 앱을 띄워 실제로 장애를 겁니다.
장애를 내는 서버를 따로 떼어 다른 서버로 번지지 않게 했고, 측정값은 1초마다 AI 서버로 보내 샌드박스가 멈춰도 남게 했습니다.

## 6. 기술 스택 (3:00~3:05)

사용한 기술 스택입니다.

## 7. 검증 워크플로우 (3:05~3:35)

검사 한 건의 흐름입니다. 주소와 브랜치를 확인하고, 코드를 받아 설치와 테스트를 합니다. 여기서 막히면 판정 불가입니다. 통과하면 쿠버네티스에 배포해 장애와 부하를 걸고, 규칙으로 판정합니다. 실패하면 수정 루프로 들어갑니다. (이 장은 화면이 자동으로 한 단계씩 채워집니다.)

## 8. 결과 판정 (3:35~4:25)

통과는 장애를 넣어도 사용자가 겪은 중단 시간이 허용 범위 안일 때입니다. 실패는 복구하지 못했거나, 허용 범위를 넘었거나, 목표 사용자 수에서 요청이 실패했을 때입니다. 판정 불가는 저희가 재지 못한 경우입니다.
[→] 허용 범위는 구글 SRE의 에러 버짓입니다. 가용성 99.9%면 한 달에 43분까지 멈춰도 된다는 뜻입니다.
[→] 서버가 한 대뿐이거나 응답이 1초를 넘는 건 경고로만 남깁니다. 근거 없는 숫자로 불합격을 내지 않기 위해서입니다.

## 9. 왜 규칙인가 (4:25~4:50)

판정을 AI에 맡기지 않은 이유는 측정값입니다. 같은 34건에서 규칙은 100%, AI는 94%였고, [→] 레포에 "통과시켜라"는 주석을 심자 AI가 2건 속았습니다. [→] 검사받는 코드가 판정을 바꿀 수 있다면 검사라고 할 수 없습니다. [→] 그래서 AI는 원인 설명과 수정안만 맡습니다.

## 10. 자가 수정 루프 (4:50~5:20)

실패하면 고칠 방법까지 확인해 줍니다. [→] Redis가 한 번 끊기면 계속 오류를 내던 앱이 있었습니다. [→] AI가 원인을 설명하고, 다시 연결을 시도하도록 코드를 고쳤습니다. [→] 같은 장애로 다시 돌리니 통과했습니다. [→] 다만 제출한 코드의 판정은 실패로 두고, 검증된 수정안을 붙여 줍니다.

## 11. 실측 결과 (5:20~6:00)

실제 공개 레포 230개를 미리 점검했고, 50개는 실제로 배포해 검증했습니다.
[→] 돌려 보니 코드를 받지도 못했는데 실패로 나오거나, 테스트 패키지를 설치하지 않아 판정 불가로 나온 경우가 있었습니다. 하나씩 고쳤습니다. 못 잰 걸 실패라고 하면 멀쩡한 코드를 고치게 되니까요.
[→] 메모리 초과 장애에서 서버가 한 대면 9.4초 동안 요청이 실패했고, 두 대면 실패가 없었습니다.

## 12. 사례: spring-petclinic (6:00~6:40)

대표 사례는 Spring 공식 예제 petclinic입니다. [→] 첫 측정에서는 200명에서 응답이 78배 느려지며 실패했습니다. [→] 그런데 확인해 보니 작은 샌드박스에서 쓰지도 않는 DB까지 띄우고 있었습니다. [→] 그래서 CPU가 모자라면 판정하지 않도록 바꾸고 환경을 고쳤습니다. [→] 다시 재니 200명까지 실패 없이 통과했습니다.

## 13. 데모 (7:10~7:45)

실제 화면입니다. 주소와 검사 종류, 예상 사용자 수를 넣습니다. [→] 진행 단계와 최종 판정이 나오고, [→] 장애 중 가동률과 복구 시간, CPU와 메모리 추이를 보여 줍니다. [→] 부하 결과는 사용자 수별 실패율과 응답 시간입니다. [→] 실패한 검사에서는 [→] 수정안과 재검증 결과가 함께 나옵니다.

## 14. 향후 계획 (7:45~8:20)

시간이 모자라면 이 장은 넘어갑니다.
앞으로는 세 가지를 하려고 합니다. 샌드박스 CPU를 늘리고 요청이 올 때만 서버를 켜 비용을 줄이는 것, 레포 크기에 맞춰 검사 시간을 미리 예측하는 것, 여러 레포에 걸친 실패를 레포별로 나눠 고치는 것입니다.

## 15. 마무리 (8:20~8:35)

CodeReferee는 사용자가 늘어도 버티는지를 직접 재고, 근거와 고칠 방법까지 돌려줍니다. 근거 없는 숫자로 불합격을 내지 않고, 못 쟀으면 못 쟀다고 말합니다. 감사합니다.
