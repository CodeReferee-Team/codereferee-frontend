Chaos Scenarios

  • Pod Kill컨테이너가 죽으면 다시 뜨는가
  • OOM메모리 한도를 넘기면
  • DB, Redis Down의존 서비스가 끊기면
  • Network지연 300ms, 패킷 손실 50%

Out of Scope

코드 버그, 스타일, 테스트 실패는 판정하지 않는다.

설치, 테스트, 기동은 장애를 걸기 위한 준비 단계다. 여기서 막히면 결과는 판정 불가.

Pod를 죽였을 때 다시 살아나는지, 메모리가 넘쳐 OOM이 났을 때, DB나 Redis가 끊겼을 때, 네트워크가 느려질 때, 그리고 동시 사용자가 200명까지 늘 때 버티는지를 봅니다. [→] 코드 버그나 스타일은 보지 않습니다. 설치하고 테스트하고 띄우는 건 장애를 걸기 위한 준비 단계일 뿐이고, 여기서 실패하면 판정 불가로 냅니다. [→] 차별점은 세 가지입니다. 정적 분석이 아니라 실제로 쿠버네티스에 띄우고 장애를 겁니다. 판정은 LLM이 아니라 규칙이 합니다. 그리고 실패하면 패치를 만들어서, 그 패치로 정말 버티는지까지 다시 돌려 보고 줍니다.

04 Architecture, Stack

서버 3대, 역할이 다르다

(3:10~3:45) 시스템은 서버 세 대로 나뉩니다. BE는 Spring Boot로 요청을 받고 결과를 Postgres에 저장합니다. BE와 AI 사이는 Redis 큐로 연결해 결과가 유실되지 않게 했습니다. AI 서버는 FastAPI와 LangGraph로 파이프라인을 돌리면서 판정과 패치를 만듭니다. 샌드박스는 쿠버네티스와 LitmusChaos로 실제 장애를 겁니다. 요청이 있을 때만 켜서 비용을 줄이고, 장애가 다른 서버로 번지지 않게 격리했습니다. 메트릭은 샌드박스 안의 Prometheus Agent가 1초 단위로 모아 AI 서버로 바로 보냅니다. 샌드박스가 장애로 죽어도 데이터는 남습니다.

05 Verdict

결과는 세 가지, 기준은 실제 다운타임

PASS통과

장애를 실제로 넣었고, 사용자가 겪은 다운타임이 에러 버짓 안이다. 목표 사용자 수에서도 요청이 실패하지 않았다.

FAIL실패

복구하지 못했거나, 다운타임이 에러 버짓을 다 썼다. 또는 적어 준 목표 동시 사용자 수에서 요청이 실패했다.

판정 불가

샌드박스에 들어가지 못했다. 설치, 테스트, 기동 실패, 테스트 없음, CPU 부족, 관측 불가. 재지 못한 것을 합격이나 실패로 몰지 않는다.

에러 버짓 가용성 99.9% = 한 달에 43.2분까지 멈춰도 된다
020% 넘으면 경고100% 다 쓰면 FAIL
기준 출처: Google SRE Book, SRE Workbook 에러 버짓 정책
경고는 판정을 바꾸지 않는다
복제본 1개복구가 예상보다 느림장애 중 응답 지연 증가일부 시나리오만 실행

복제본 1개는 사용자의 선택이다. 근거 없는 임계값으로 FAIL을 내지 않고 리포트에 남긴다.

(4:40~5:20) 통과는 장애를 실제로 넣었고, 사용자가 겪은 다운타임이 에러 버짓 안에 있을 때입니다. 실패는 복구하지 못했거나, 다운타임이 버짓을 넘었거나, 목표 동시 사용자 수에서 요청이 실패했을 때입니다. 판정 불가는 샌드박스에 들어가지 못했을 때입니다. 재지 못한 걸 합격이나 실패로 몰지 않습니다. [→] 에러 버짓은 구글 SRE에서 쓰는 개념입니다. 가용성 99.9%면 한 달에 43.2분까지 멈춰도 된다는 뜻이고, 버짓의 20%를 넘으면 경고, 다 쓰면 실패입니다. [→] 복제본이 1개라거나 복구가 예상보다 느린 건 경고로만 남기고 판정은 바꾸지 않습니다. 근거 없는 기준으로 실패를 내지 않기 위해서입니다.

06 Case Study

spring-petclinic, 목표 동시 사용자 200명

동시 사용자별 응답 시간 p95 (ms, 재측정 결과)
FAIL첫 측정: 200명에서 목표 미달

100명까지는 버텼고 200명에서 p95가 78배로 뛰며 요청이 시간 초과. Critic은 "복제본 1개라 여유가 없다"고 짚었다.

의심이게 앱의 한계인가, 샌드박스의 한계인가?

2코어 노드에서 앱이 쓰지도 않는 MySQL, Postgres까지 띄워 CPU를 나눠 쓰고 있었다. 측정 환경이 공정하지 않았다.
